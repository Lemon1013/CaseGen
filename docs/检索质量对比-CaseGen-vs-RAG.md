## 四、根因分析

### 4.1 CaseGen 的优势来源

| 机制 | 作用 | 例子 |
|---|---|---|
| **Wiki 提炼层** | 模型预先提炼成专题页，标题即主题 | `竞价交易单笔成交金额计算与精度规则` |
| **条款锚点** | 按条款号（4.1.3、3.6.9）精确定位 | 查询"收盘价"直接命中 4.1.3 |
| **BM25 关键词** | 精确词匹配 | "收盘价"命中标题含该词的页 |
| **融合排序** | 多路结果加权合并 | 原文+Wiki 混合排序 |

### 4.2 RAG 的短板

| 短板 | 表现 |
|---|---|
| **纯向量无语义重心** | 查询"撤单 订单状态"命中"累计成交金额" |
| **无结构感知** | 不知道 4.1.3 是收盘价定义条款 |
| **无提炼层** | 只有原始分块，无主题页 |
| **长文档定位弱** | 规则文档 65KB，分块后相似度区分度低 |

### 4.3 RAG 的唯一潜在优势

| 优势 | 说明 | 本次是否体现 |
|---|---|---|
| 语义泛化 | 换个说法也能命中 | 未体现，8 组查询都用原文术语 |
| 无需维护 Wiki | 直接吃原始文档 | 是优势，但换来质量下降 |
| 跨文档统一 | 一个库查所有 | 是优势，但 CaseGen 也能跨 space |

## 五、结论

**当前配置下，OpenAI RAG 明显不如 CaseGen 现有混合检索。**

关键判断：
1. **不建议直接替换**：8:0 全败，且 3 组明显偏题
2. **RAG 缺的是结构化检索能力**：条款锚点、Wiki 提炼、关键词精确匹配
3. **纯向量检索在专业文档上不够用**：专业术语（收盘价、撤单）需要精确匹配

## 六、可能的改进方向

如果要用 RAG，需要补强：

| 改进 | 说明 |
|---|---|
| **混合检索** | RAG 向量 + BM25 关键词，两路融合 |
| **元数据过滤** | 给分块打上章节号、文档类型标签，检索时过滤 |
| **查询改写** | 把"收盘价"扩展成"收盘价 4.1.3 加权平均价" |
| **分层检索** | 先检索章节，再检索章节内分块 |
| **保留 Wiki 层** | CaseGen 的 Wiki 提炼是核心资产，不应丢弃 |
