# 规则-only v3（规则+补充需求说明）真实覆盖率评测

评阅人：主代理本人逐条对照。日期：2026-10-21（北京时间）。

**输入：交易规则 DOCX（doc6）+ 竞价交易系统需求说明补充文档（doc7），无回归清单。**

## 一、总体结果对比

| 模块 | 基准 | v1 | v2 | **v3** |
|---|---:|---:|---:|---:|
| 集合竞价撮合 (AUC) | 19 | 3 | 3 | **3** |
| 单笔成交金额 (AMT) | 14 | 0 | 0 | **2** |
| 累计成交金额 (ACC) | 13 | 0 | 0 | **1** |
| 开盘价 (OPN) | 19 | 1 | 2 | **4** |
| 收盘价 (CLS) | 22 | 0 | 0 | **0** |
| 撤单订单类型 (CAN) | 26 | 0 | 0 | **8** |

**完整覆盖从 4.4% 提升到 15.9%，翻了 3.6 倍。补充文档确实有效。**

## 二、逐模块评阅

### 2.1 单笔成交金额（2/14，v2 为 0）

**改善**：v3 直接表达了金额计算口径与精度规则。

| 基准 | 判定 | 依据 |
|---|---|---|
| AMT-001 三位小数×常规买量 | ⚠️ 部分 | TP-001 表达计算口径，TP-003/004 表达精度，但缺"常规买量"这一数量类别 |
| AMT-009 一位整数价格×常规买量 | ⚠️ 部分 | 同上 |
| AMT-013 价格下边界 | ✅ **覆盖** | TP-007/008 明确"价格与数量须在有效范围内，超范围无效申报" |
| AMT-014 价格上边界 | ✅ **覆盖** | 同上 |
| AMT-002~008 精度×阈值组合 | ❌ 未覆盖 | 补充文档只给"精度是什么"，没给"精度与阈值的组合测试" |
| AMT-010 四位整数×常规买量 | ⚠️ 部分 | TP-001 计算口径 |
| AMT-011/012 两笔联合条件 | ❌ 未覆盖 | 无多笔逐笔计算的组合表达 |

### 2.2 撤单订单类型（8/26，v2 为 0）

**这是最大改善。** v3 建立了"订单类型×状态"的维度。

| 基准 | 判定 | 依据 |
|---|---|---|
| CAN-001 限价×失败 | ✅ 覆盖 | TP-003（失败无撤单对象）+TP-009（限价类） |
| CAN-002 限价×未成交 | ✅ 覆盖 | TP-009 明确"限价类+未成交+允许时段+已确认" |
| CAN-003 限价×部分成交 | ✅ 覆盖 | TP-011 明确"限价类+部分成交+仅撤未成交部分" |
| CAN-004 限价×全部成交 | ✅ 覆盖 | TP-004（全部成交不允许撤） |
| CAN-005 限价×已撤销 | ✅ 覆盖 | TP-005（已撤销不允许重复撤） |
| CAN-006~010 本方最优×5状态 | ⚠️ 部分 | TP-010/021 提到"市价类可细分本方最优"，但未逐一展开5状态 |
| CAN-011~015 对手方最优×5状态 | ⚠️ 部分 | 同上 |
| CAN-016~020 市转限×5状态 | ⚠️ 部分 | TP-021 提到"市价转限价"，未展开 |
| CAN-021~025 市转撤×5状态 | ⚠️ 部分 | TP-021 提到"市价即时成交剩余撤销"，未展开 |
| CAN-026 撤单成功 | ✅ 覆盖 | TP-001（未成交+确认→撤销成功） |

**说明**：限价类 5 个状态被完整覆盖，市价类 4 个子类型只表达了"存在这些类型"，未展开状态矩阵。所以 8 项完整覆盖集中在限价类和通用规则。

## 三、严重的新问题

### 3.1 补充文档内容被大量"照抄"成场景

看这些场景：

```
ACC TP-034  限价类：投资者指定委托价格，成交价格不优于委托价格
ACC TP-038  失败 | 订单未被交易系统接受，未进入撮合
ACC TP-042  撤单请求需同时满足以下条件方被受理：1. 订单处于可撤销状态...
CAN TP-029  覆盖"五、撤单处理"章节的撤单处理场景
CLS TP-029  累计成交金额的展示精度是否与计算精度一致，本文档暂未明确
CLS TP-030  各具体产品的价格精度、金额精度...本文档暂未明确
CLS TP-031  市价类各子类型的具体适用条件与优先级，本文档暂未明确
```

**模型把补充文档的段落、表格行、甚至"待确认事项"直接当成了场景。** 这是典型的"文档抄写"，不是"测试设计"。

更荒谬的是 `CLS TP-029~031`：这些是补充文档第七节的"待确认事项"，被当成收盘价的测试场景了。

### 3.2 补充文档内容跨模块污染

| 现象 | 例子 |
|---|---|
| 累计金额场景跑到单笔金额任务 | AMT TP-012~015 讲累计成交金额 |
| 订单类型/撤单内容跑到累计金额任务 | ACC TP-034~050 讲订单类型、撤单 |
| 撤单规则跑到收盘价任务 | CLS TP-035 讲停牌撤单 |
| 金额计算跑到集合竞价任务 | AUC TP-015 讲单笔金额计算 |

**原因**：doc7 只有 2727 字符、6 个 Wiki 页面，检索时很容易把整篇内容都拉进来，不分章节。

### 3.3 "待确认事项"被当成有效场景

补充文档第七节列了 4 条待确认事项，结果被生成成：
- `CLS TP-029/030/031`（收盘价任务）
- `CAN TP-033/034/035`（撤单任务）
- `AUC TP-045/046/047/048`（集合竞价任务）

这些场景内部核验会判 full（确实表达了"待确认"这个事实），但对基准覆盖零贡献。

## 四、结论

### 4.1 补充文档确实有效

| 指标 | v2 | v3 | 提升 |
|---|---:|---:|---|
| 完整覆盖 | 5 (4.4%) | 18 (15.9%) | **+13 项，3.6倍** |
| 撤单模块 | 0/26 | 8/26 | 显著 |
| 单笔金额 | 0/14 | 2/14 | 从无到有 |

**方向正确，补充业务规则文档是提升覆盖率的有效手段。**

### 4.2 但有严重的质量问题

| 问题 | 表现 |
|---|---|
| 文档抄写 | 把补充文档的段落、表格行直接当场景 |
| 跨模块污染 | 金额规则跑到撮合任务，撤单规则跑到收盘价任务 |
| 待确认项被当场景 | 4 条待确认事项生成了 10+ 个"场景" |
| 内部核验失真 | 上述场景都判 full，内部 6/6 complete 但真实覆盖仅 15.9% |

### 4.3 提升空间在哪

| 模块 | 当前 | 瓶颈 |
|---|---|---|
| AMT | 2/14 | 缺"精度×阈值×数量类别"的组合指引 |
| ACC | 1/13 | 缺具体尾数场景 |
| CLS | 0/22 | 补充文档未涉及收盘价的具体成交分布 |
| CAN | 8/26 | 缺市价类4子类型×5状态的展开 |
| AUC | 3/19 | 缺具体候选价位组合 |
| OPN | 4/19 | 缺具体申报分布 |

**共同瓶颈：补充文档给了"规则是什么"，但没给"怎么组合测试"。**

## 五、建议

1. **补充文档需要增加"组合维度"说明**：例如"金额场景需覆盖价格精度×数量类别×阈值边界的组合"，而不是只描述精度定义。
2. **检索需要按章节隔离**：避免 doc7 的整篇内容被拉进每个任务，造成跨模块污染。
3. **补充文档的"待确认事项"应移除或改写**：它们被误当成场景，纯属噪音。
4. **内部核验需要识别"文档抄写"类场景**：现在抄段落也能判 full，掩盖了真实缺口。
