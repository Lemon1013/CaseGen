# 全场景评测操作说明

记录日期：2026-10-20。本文说明如何读取**最新一批**六模块场景，并与有效 113 项基准做比对。

## 0. 先看这个：当前存在一个阻断

**最新批次（164 场景）没有对应的评测输入，不能直接开跑。**

原因：

- 最新 164 场景是通过 API **整阶段重试**产生的（任务20～25 的 CP23/25/24/26/29/27）。
- 而生成工具的归档 `data/validation/full-coverage-20261019T120957376924Z-bb42787d/` 记录的是**首次生成**的旧检查点（如 CLS 冻结在 CP20 / 51 点，实际现为 CP29 / 28 点）。
- 评测工具 `evaluate_full_coverage.py prepare --campaign` 只认这个归档，会读到**旧场景池**，不是最新批次。

所以要做评测，必须先把最新批次导出为评测输入。两条路：

- **方案 A（推荐）**：从数据库只读导出最新检查点为评测输入文件，再用 `prepare --input`。
- **方案 B**：重新跑一次生成工具（会新建任务，产生新批次，成本高）。

下面按方案 A 写。

## 4. 导出最新批次为评测输入

评测工具支持 `prepare --input <json>` 读取通用场景文件。需要构造：

```json
{
  "input_id": "full-current-20261020",
  "scenarios": [
    {
      "id": "TP-20-<point_id>",
      "category": null,
      "title": "<test_points.title 原文>",
      "description": "<test_points.verification_goal 原文>",
      "test_focus": "<test_points.verification_goal 原文>",
      "text": "<title>\n<verification_goal>",
      "source_task_id": 20,
      "source_point_id": <point_id>,
      "source_checkpoint_id": 23
    }
  ],
  "reference_material": [
    {"source_id": "...", "source": "冻结检索已选正文", "text": "..."}
  ]
}
```

导出要点（必须遵守，否则评测不可信）：

1. **正文逐字**：`title` 用 `test_points.title` 原值，`verification_goal` 原值，不做任何改写。
2. **只取最新检查点**：按上表 `checkpoint_id` 过滤，不混历史批次。
3. **不喂判定标签**：导出文件里绝不能带 `coverage_metadata`、`full/missing` 状态、人工结论、旧评测结果。
4. **参考材料**：来自各任务已确认检索快照中**已选**来源（`task_retrieval_checkpoints.selected_citation_ids_json` 对应的 `retrieval_json` 内容），不读新的知识库文件。
5. **完整对象另存**：原始 point 全字段与 citation 关联单独存快照文件，供追溯，但不进评测输入。

### 可直接运行的导出脚本

`test_points` 表实际字段：

```
id, task_id, checkpoint_id, stable_key, title, verification_goal,
dimension, priority, sort_order, is_selected, is_excluded, created_at, updated_at
```

导出脚本（只读，不写库）：

```bash
backend/.venv/bin/python - <<'PY'
import json, sqlite3
from pathlib import Path

LATEST = {20: 23, 21: 25, 22: 24, 23: 26, 24: 29, 25: 27}  # 模块 → 最新检查点
DB = 'file:data/meta/app.db?mode=ro'
OUT = Path('data/evaluation/scenario-benchmark-v0.1/inputs/latest-164.json')
OUT.parent.mkdir(parents=True, exist_ok=True)

conn = sqlite3.connect(DB, uri=True)
scenarios = []
for task_id, cp_id in LATEST.items():
    rows = conn.execute(
        'select id, title, verification_goal, dimension, priority, sort_order '
        'from test_points where checkpoint_id=? and is_selected=1 and is_excluded=0 '
        'order by sort_order, id', (cp_id,)).fetchall()
    for pid, title, goal, dim, prio, order in rows:
        scenarios.append({
            'id': f'TP-{task_id}-{pid}',
            'category': None,
            'title': title,                 # 逐字原文
            'description': goal,            # 逐字原文
            'test_focus': goal,             # 逐字原文
            'text': title + '\n' + goal,    # 与既有投影一致
            'source_task_id': task_id,
            'source_point_id': pid,
            'source_checkpoint_id': cp_id,
        })

payload = {
    'input_id': 'full-current-20261020',
    'scenarios': scenarios,
    'reference_material': [],   # 见下方说明，需单独补
}
OUT.write_text(json.dumps(payload, ensure_ascii=False, indent=1))
print('exported', len(scenarios), 'scenarios ->', OUT)
PY
```

运行后应输出 `exported 164 scenarios`。

**参考材料的补充**：`reference_material` 需要从各任务的已确认检索快照取已选来源正文。若不补，评测仍可运行，但裁判缺少规则原文参考，业务一致性判断会偏保守（更多 `not_assessed`）。补齐方式：

```bash
backend/.venv/bin/python - <<'PY'
import json, sqlite3
conn = sqlite3.connect('file:data/meta/app.db?mode=ro', uri=True)
LATEST = {20: 23, 21: 25, 22: 24, 23: 26, 24: 29, 25: 27}
refs = {}
for task_id, cp_id in LATEST.items():
    ret = conn.execute(
        'select retrieval_json, selected_citation_ids_json '
        'from task_retrieval_checkpoints where task_id=? '
        'order by attempt desc limit 1', (task_id,)).fetchone()
    snapshot, selected = json.loads(ret[0]), set(json.loads(ret[1]))
    for hit in (snapshot.get('context') or {}).get('source_hits') or []:
        cid = hit.get('task_citation_id')
        text = hit.get('content') or hit.get('text') or ''
        if cid not in selected or not text:
            continue
        # 同一文档同一区间只保留一份，记录全部依赖
        key = (hit.get('document_id'), hit.get('start_char'), hit.get('end_char'))
        refs.setdefault(key, {'source_id': f'doc{hit.get("document_id")}:{hit.get("start_char")}-{hit.get("end_char")}',
                              'source': '冻结检索已选正文', 'text': text,
                              'tasks': set()})['tasks'].add(task_id)
out = [{'source_id': v['source_id'], 'source': v['source'], 'text': v['text'],
        'tasks': sorted(v['tasks'])} for v in refs.values()]
print(json.dumps(out, ensure_ascii=False)[:400])
print('refs', len(out))
PY
```

确认无误后把 `out` 填入导出文件的 `reference_material`（去掉 `tasks` 字段或保留作溯源均可）。

## 5. 执行评测

```bash
RUN=data/evaluation/scenario-benchmark-v0.1/runs/full113-current-20261020-latest

# 准备（零 HTTP、零凭据）
/usr/bin/python3 -B tools/scenario_benchmark/evaluate_full_coverage.py prepare \
  --input <导出的input.json> \
  --database data/meta/app.db \
  --input-id full-current-20261020 \
  --target-size 5 \
  --output-dir $RUN

# 先单批验证额度，再批量
/usr/bin/python3 -B tools/scenario_benchmark/evaluate_full_coverage.py run \
  --run-dir $RUN --execute --smoke
/usr/bin/python3 -B tools/scenario_benchmark/evaluate_full_coverage.py run \
  --run-dir $RUN --execute --resume

# 离线严格重放审计（不发 HTTP）
/usr/bin/python3 -B tools/scenario_benchmark/evaluate_full_coverage.py audit \
  --run-dir $RUN
```

参数说明：

| 参数 | 作用 |
|---|---|
| `--database` | 只读打开业务库，取清单外已选来源全文；不写库 |
| `--target-size 5` | 每批输出 5 个目标，越小越稳；可选 1～5 |
| `--max-request-bytes` | 请求体上限，默认 1MiB，最大 2MiB。164 场景预计 1MiB 内，若超限再加 |
| `--smoke` | 只跑第一批，用于验证额度与协议 |
| `--resume` | 续跑，已完成批次严格重放跳过、不重复计费 |

## 6. 与基准比对的口径

工具自动产出：

- **A 阶段**：113 项基准逐项判定 `full / partial / missing / unresolved`
- **B 阶段**：每条候选判定 `matched / new / extension / unresolved / out_of_scope`，以及粒度、业务一致性、重复组

报告文件（在 `$RUN` 下）：

```
session-NNN/report.md          # 人读报告
session-NNN/report.json        # 机读完整结果
baseline-113.csv               # 113 行逐项
candidates-448.csv             # 候选逐条
```

解读时必须注意：

1. **`full` 只表示"基准条件被候选明确表达"**，不证明金额算法、撮合逻辑正确。
2. **`new` 只表示"相对有效 113 未匹配"**，不是"合理新增"，需人工核查。
3. **`matched` 不是覆盖数**：多条候选可匹配同一基准，一条候选也可匹配多个基准。
4. **B 阶段映射来自 A 阶段真实边的确定性反转**，不是第二次独立盲评。
5. **技术失败 ≠ missing**：429、超时、格式失败单独记录，不能算作未覆盖。

## 7. 额度与失败处理

历史经验：模型额度是**账户级**的，会中途耗尽。

- 遇到 HTTP 429 `rate_limit_error: The usage limit has been reached` → 停止，等额度恢复
- 单批重试预算用尽后，**必须新建运行目录**，并迁移已成功批次（`cp -a` 各 `requests/A-*`、`B-*`），否则续跑不会发出新请求
- 成功批次会严格重放校验并跳过，不重复计费
- 当前公开配置只有 `magpie` 一个可用评测通道（`new-api` 预检失败），无法切换
